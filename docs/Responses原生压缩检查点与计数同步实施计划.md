# Responses 原生压缩检查点与计数同步实施计划

用户已授权执行同步，必须保护旧客户端压缩。实施核心为有效历史检查点、恢复计数和实际请求前容量保护，沿用现有 Responses context_management 和显式 responses_compact_threshold。保留通用历史供展示、rewind 和跨协议回退；不改变关闭原生模式时的客户端摘要与后台预压缩逻辑。Codex 专用 compaction_trigger 与异步压缩依赖上游能力，作为后续独立扩展。

## 实施

1. sampling-types 提供统一原生投影结果：有效 input、选中压缩点、可验证用量基线及来源。继续核对实际认证来源、准备后的历史前缀、同响应内顺序和工具配对。
2. 完整成功响应中保存客户端签发的有效历史检查点与用量记录，兼容旧历史；恢复通过检查点和后续内容重建模型有效窗口，消除仅靠进程内基线的问题。
3. 上下文计数与账单分离；context_details 优先，缺少时估算，后续正常响应 usage 校准。统一流式/非流式，保留来源和覆盖范围，贯通界面快照。
4. SamplingClient 完成图片过滤、认证和投影后对实际发送内容做原生容量检查，计入工具和输出预留。超限阻止网络请求，以有界恢复调用现有客户端压缩并重新准备。旧模式保持原检查。
5. 原生路径避免对 raw 历史重复估算。历史改写、切源、手动压缩、rewind/fork 由检查点验证和重建处理；禁止重新放行被清理内容。
6. 检查点随历史对象一起持久化，避免单独文件错配；保留写入错误，不宣称失败的写入已持久化。

## 实施结果

- 有效压缩点和计数锚点随会话历史保存，普通响应只新增小型哈希与用量记录。请求层统一完成来源、历史前缀、工具配对及容量检查，计入工具定义和输出预留。
- 服务端报告值与请求安全预算分开，避免工具结果待配对时把本地归档估算显示为模型实际上下文。压缩响应缺少精确上下文时标记估算，后续普通响应校准；账单用量独立保留。
- 修复冷恢复模型时重写系统提示、丢失创建时规则的问题。恢复明确使用保留提示策略，主动切换模型沿用现有策略，显式系统提示覆盖继续走独立入口。
- 未配置原生阈值时保留旧百分比压缩、后台预压缩和手动压缩。原生容量超限最多尝试一次客户端摘要恢复。
- `/context` 展示原生阈值与计数来源；压缩后的总量统一展示为有效上下文，本地分类明细明确标记估算。
- 本地完整历史继续保留，文件仍会增长。Codex 专用触发参数、异步压缩与独立压缩接口仍作为依赖上游能力的后续扩展。
